## 0. 评审结论摘要

roadmap 的地基（M0 + 检索正确性铁律）成立，"grep 管存在、LLM 管意义"方向正确；
但初版存在**定位分裂（个人工具认领企业平台野心）**、**成本哲学被写入路径掏空**、
**里程碑估时失真**、**引文回流洗白风险**、**度量空心化**五类问题。以下逐条裁决。

## 1. 裁决记录（Q1-Q11）

### Q1 · 定位分裂 —— ✅ 已裁决

**问题**：§1 写"个人优先、中小企业次之"，M3-M6 却全为企业场景盖楼（API 白名单、
S3/飞书云盘、监控看板、OAuth、公网门户）。单维护人 3 天大的项目承诺了五种外壳的攻击面。

**主人裁决**：**目标用户 = 个人知识库（第二大脑）用户，缩小使用范围，去掉中小企业盖楼。**

**落地动作（roadmap 修订时执行）**：
- §1 定位表删除"中小企业本地化部署次之"
- 形态 E（公网搜索页）整节删除（见 Q9）
- §4.5"企业级摄取"改名"摄取增强"，剔除企业叙事；S3/飞书云盘/RSS 降级为"按需扩展点"，不进里程碑
- M5/M6 里程碑合并精简（见 Q7 拆解）
- §2.2 交付形态由五种收敛为三种：**CLI / 智能体技能 / 本地 Web UI**（对外 API 保留但定位改为"局域网内个人设备/程序互联"，不做企业租户）

### Q2 · 与本机第二大脑的关系 —— ✅ 已裁决

**问题**：同主机已有 second-brain（采集→梦境→Wiki→图谱 全自动流水线），roadmap 的
M1（关联/图谱）与 M4（定期洞察）与其功能重叠，零字提及边界，存在语料双份、
两套图谱互不相认的战略风险。

**主人裁决**：**本机第二大脑是基于 OpenClaw 智能体定制的私有版本；CENHUA 是承袭其
思想的重构升级，目标是独立产品项目。** 即：思想同源、产品独立、不整合、不双写。

**落地动作**：
- roadmap §1 增加"与 OpenClaw 第二大脑的关系"小节：CENHUA 是通用化独立产品，
  不假设用户有 OpenClaw；本机 second-brain 是其孵化环境而非依赖
- 文档中所有 `file:///home/world/solo/...` 内部链接清除（私人主机路径不属于公开产品文档，见 Q11）

### Q3 · 写入路径成本失控 —— 📐 方案已给出

**问题**：§5.3 摄取时默认自动 LLM 总结（`CENHUA_SUMMARY=on`）+ §5.5 NER，把 LLM
塞进每一条写入路径——**每份文档进库自动多打一轮 LLM，哪怕永不被查询**。
已落地的护栏只管 `ask`，写入侧无成本立案。

**方案：写入侧三道闸门（默认免费，按需付费）**

1. **规则先行（免费层）**：摄取时只做零成本动作——
   首段截取、正则实体粗提（金额/日期/邮箱/证件号/大写实体）、TF 关键词、
   标题结构（树索引已有）。总结占位 `status=rule-only`。
2. **按需精化（延迟付费）**：LLM 总结/NER 不在摄取时跑，改为触发式：
   - 文档**首次被 `query`/`related` 命中**时入精化队列（此时用户价值明确）
   - 或 `cenhua refine --all --dry-run` 手动批量，先估价再执行
   - 队列持久化在 `<vault>/meta/refine_queue.jsonl`，`cenhua refine --drain` 消费
3. **预算硬闸（货币层，配合 Q4）**：
   - `CENHUA_REFINE_BUDGET_CNY`（默认 0 = 只允许规则层；设值才允许 LLM 精化）
   - 每次精化批次前：估算 token → 换算金额 → 超预算即拒，需 `--force` 或调预算
   - 台账 `<vault>/meta/cost-ledger.jsonl`：每次 LLM 调用记 `{ts, cmd, doc, calls, tokens_in, tokens_out, est_cost}`，`cenhua cost [--month]` 汇总
4. **批量折扣技巧**：精化队列攒批，单次请求合并 5-10 份短文档的总结任务，摊薄每文档开销

**新默认值**：`CENHUA_SUMMARY` 默认从 `on` 改为 `deferred`（规则先行+按需精化）。

### Q4 · dry-run 预估 token 金额 —— ✅ 已裁决采纳

**问题**：护栏全是调用**次数**（`max_llm_calls=8`），一次 500 页大文档树导航的
token 可以是小文档 20 倍，次数护栏对成本形同虚设。

**落地动作**：
- `--dry-run` 输出从"预估 calls"升级为"预估 calls + tokens + 金额"：
  `预计 6 次调用 · ~48K in / 12K out · ≈¥0.35（按 model 单价表）`
- 单价表 `pricing.json`（随包分发，可覆盖）：model → {in, out} 每 1K token 价格；未知模型用保守默认价并在输出标注"估价，未配置单价"
- 新配置 `CENHUA_MAX_COST_CNY`（单命令花费上限，默认 2.0），与 `max_llm_calls` 并联，先到先停
- `max_llm_calls` 保留为辅助护栏，不再是唯一护栏
- token 估算方式：字符数/1.6（中英混合近似）+ 上次真实调用的校准系数，不追求精确、追求数量级正确
- 全部写入 Q3 的 cost-ledger，形成"预估 vs 实际"闭环（预估偏差>3x 时告警，防单价表过期）

### Q5 · 实体共现关联降噪 —— 📐 方案已给出

**问题**：高共现实体（如出现 200 次的公司名）会让全库变全连接毛球，0.8 权重
名不副实。要求：严格控制的基础上保障可用。

**方案：四层降噪，规则全免费**

1. **IDF 过滤（自动）**：实体 IDF = `log(N/df)`；`df > N×0.30`（出现在超过 30% 文档）
   判为"枢纽实体"，**不产生共现边**，只保留在实体索引里可查。
2. **共现显著性 PMI（自动）**：边权不用共现次数，用归一化 PMI：
   `nPMI(A,B) = log(N·|D_A∩D_B| / (|D_A|·|D_B|)) / log(N)`；
   `nPMI ≤ 0`（共现不超过随机期望）直接不建边。
3. **共现地板（自动）**：`|D_A∩D_B| < 2`（只同现于 1 份文档）不建边，防偶然噪音；
   每篇文档对外关联**截断 Top-8**，宁缺毋滥。
4. **人工阀门（免费）**：`cenhua link --ban <实体A> <实体B>` 黑名单永久压制；
   `cenhua hub` 列出被判定的枢纽实体供人工复核（误杀则降阈值例外放行）。

**可用性保障**：`related` 输出每条边带**证据**（`evidence: "共现于 [docA P3, docB P12], nPMI=0.41"`），
空结果明示"无显著关联（正常）"而非沉默——关联为空本身是信息。
权重语义修订：0.8 只属于人工显式关联（`cenhua link`）；自动共现边权重上限 0.6。

**实现位置**：`m_graph.py` 建边函数，纯 Python 统计，零 LLM 零依赖，预计 <300 行。

### Q6 · Service 层解耦 —— 📐 方案已给出

**问题**：原则 7 宣称"核心服务层与前端解耦、CLI 是薄包装"，但 service 层**不存在**
（实查 `scripts/` 九个 m_*.py 直接是 CLI 本体）。roadmap 用一句"M3 起需补 service 层"
把架构欠账伪装成文档补充，导致 M3 估时严重失真。

**方案：绞杀者模式渐进抽取（不动刀大爆炸）**

1. **先立契约后搬家**：新增 `cenhua_service/__init__.py`，定义 6 个函数签名（不实现）：
   ```python
   ingest(paths|urls, vault) -> IngestReport
   find(terms, vault, doc=None) -> list[Hit]
   query(q, vault, budget) -> QueryResult        # 三路融合+延展
   related(doc, vault, top=8) -> list[Relation]
   ask(q, vault, doc=None, budget) -> AskResult  # 含 citations
   stats(vault) -> VaultStatus
   ```
   返回全部为 dataclass（字段名即 API 契约，Web/API 直接序列化）。
2. **每个里程碑搬一块**：M1 搬 summarize/related；M2 搬 query/ingest(web)；
   M3 只剩"把 FastAPI 挂到已有 service 函数上"——Web UI 届时才名副其实是薄包装。
   **禁止在 service 里 print**：只返回数据，CLI 的 stdout 格式化留在 m_*.py。
3. **防回潮测试**：新增 `test_70_service_no_print`（service 模块禁 print/exit）+
   `test_71_cli_is_thin`（CLI 函数体 ≤10 行：解析参数→调 service→渲染）。
4. **工作量真实记账**：抽取随功能走，边际成本 ≈每命令 +20% 开发量，不单独立项，
   但计入各里程碑验收（见 Q7）。

### Q7 · M3 拆分 —— 📐 方案已给出

**问题**：M3 同时捆绑 Web UI + 对外 API + digest + service 层欠账 + Docker，违反
自己"每个里程碑可独立交付"的规矩；且 M2 内部（网页收录不依赖 M1）被串行链白白拖住。

**方案：拆细 + 松依赖**

```
M1  v0.2  编织基础（总结 deferred 化 + 降噪关联 + service: related/summarize）
M2a v0.3  网页收录（Playwright+readability；★不依赖 M1，可与 M1 并行开发）
M2b v0.3  延展检索 query（依赖 M1 关联层 + M2a 语料；service: query）
M3a v0.4  service 层完成 + digest（CLI-only 交付，纯后端，无前端风险）
M3b v0.5  本地 Web UI（FastAPI 挂在 M3a 的 service 上 + Jinja2/HTMX + SSE）
M4  v0.6  知识图谱 + 主题创作 draft
```

- 每格失败只砍自己：M2a 网页收录黄了不影响 M2b 检索升级；M3b Web UI 黄了
  产品仍是完整 CLI（个人用户 90% 场景）
- 对外 API 不单列里程碑：M3a 的 service 层天然可被 FastAPI 包一层，`/api/v1/*`
  作为 M3b 的顺手交付（局域网 token 鉴权即可，去企业租户化——见 Q1）
- 依赖图修正：`M1 → M2b → M3a → M3b`；`M2a` 独立支线汇入 M2b；M4 依赖 M3a 而非 M3b

### Q8 · 原件层 vs 衍生层（引文洗白） —— ✅ 已裁决补充

**问题**：digest/draft 回流进库后，后续检索命中衍生文档、LLM 基于衍生再总结，
输出看似带 `[doc P页]` 实则多层转述——provenance laundering。

**落地动作（写入 roadmap §7.3/§15.3 + 原则 6 增补）**：
1. **双层标记**：摄取台账新增 `tier` 字段：`primary`（原件/网页快照=事实源） vs
   `derived`（digest/draft/总结）。衍生文档入库强制带 `derived_from: [原件 doc_id...]`。
2. **检索默认降级**：`find/query/seek` 默认**只在 primary 层召回**；
   `--include-derived` 显式开启，且衍生命中必须显示 `⚠ 衍生内容（由 X 生成）`。
3. **引文穿透**：衍生文档被作为依据时，输出必须列 `derived_from` 链，引文最终
   指向 primary 原件页码；LLM prompt 组装时**禁止引用衍生文档的正文**（可引用其
   指向的 primary 片段）。
4. **图谱隔离**：衍生文档不参与实体共现建边（digest 罗列全库实体，参与建边=噪音炸弹）。

### Q9 · 公网搜索页 —— ✅ 已裁决

**主人裁决**：**删除公网搜索页功能。**

**落地动作**：roadmap 删除 §3.5、§6.5、M6 公网搜索部分、§13"公网搜索页 LLM 滥用"
风险行；形态收敛为三种（见 Q1）。理由备案：与"本地优先、数据主权"定位冲突，
个人用户无维护"已发布"标签纪律的前提，真实需求出现时另立项评估。

### Q10 · 验收标准补检索质量 —— ✅ 已裁决

**落地动作**：§8"里程碑验收通用标准"新增第 7 项：

> **检索质量**：每个 vault 维护固定 QA 集（`meta/qa/benchmark.jsonl`，≥30 题：
> 存在性 15 + 溯源 10 + 拒答 5），发布前跑 `cenhua bench`：
> - 存在性召回 100%（铁律"沉默不是证据"的直接度量，回归即阻断发版）
> - 引文准确率 ≥95%（引用页码经 `draft --verify` 同源校验器验证真实存在）
> - 拒答正确率 ≥90%（语料外问题必须答"没有"，防幻觉）
> QA 集与结果提交入库（`meta/qa/results/`），指标只许持平或上升。

QA 集冷启动：从 pitfalls.md 实战案例反向出 10 题 + 用户真实提问沉淀，一次 <1 小时。

### Q11 · 文档卫生（版本记号/坏块/死链） —— ✅ 已裁决

**问题**：P3/P4/P5 与 v0.2-v1.0 两套记号全文混用无映射；§15.2 检索流代码块内容截断；
公开仓库文档内 `file:///home/world/...` 本机绝对路径全部是外部死链。

**落地动作**：

   P3→v0.2/v0.3（总结·关联→v0.2，网页·query→v0.3）、P4→v0.4/v0.6、P5→删除（不再立项）
2. 修复 §15.2 截断代码块（重写完整三路融合流程图）
3. **`file:///` 绝对路径全清**：仓内引用改相对链接（`design.md`、`pitfalls.md`）；
   仓外私人参考（lark2claw_route、solo/AGENTS.md、send-report-to-feishu）**删链接保经验**——
   模式描述留在正文，出处改"内部项目实践"

## 2. 修订后里程碑总览（裁决合成）
